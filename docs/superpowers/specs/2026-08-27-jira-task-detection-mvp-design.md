# Meeting Copilot — MVP: автопостановка задач в Jira

Дата: 2026-08-27
Статус: дизайн одобрен, spec написан, план реализации ещё не создан

## Контекст и гипотеза

Разворот от «AI-суфлёр на собеседованиях» (см. `rinat_gtm_project` в памяти —
ветка приостановлена, не отменена) к продукту для **повторяющихся рабочих
созвонов**. Собеседование — редкое событие (~4 раза в год на человека), низкая
платёжеспособность из-за частоты; рабочие созвоны происходят каждый день.

**Цель MVP:** на созвоне кому-то устно поручили задачу → человек может
забыть/полениться её записать → система сама детектит (кто, что именно
поручено) → автоматически создаёт тикет в Jira на конкретного исполнителя.
Убрать человеческий фактор на этапе «запомнить и завести задачу».

**Вторая фича — явно вне рамок этого документа.** «Саммари для саммари»
(проактивная персональная подсветка релевантного тем, кто пропустил созвон, по
истории прошлых встреч) обсуждалась на уровне общих архитектурных принципов
(совместима с этим MVP, работает параллельно поверх того же захвата звука, без
векторного поиска — саммари прошлых встреч целиком в промпте), но
поток/триггеры/доставка не проработаны и намеренно отложены до отдельного
раунда брейнсторминга.

## Разбор конкурентов (кратко)

- **Granola AI** — тихий захват системного звука, «Brief» с контекстом из
  прошлых встреч перед предстоящей — ближе к второй фиче, но для будущей
  встречи, не для разбора пропущенной.
- **Fireflies.ai** — bot-join, AskFred/Meeting Search — оба pull (нужно
  спросить самому), ничего проактивного. Jira в интеграциях не найден.
- **Otter.ai** — автоматическое email-саммари пропустившим встречу в течение 2
  часов, но обезличенное, не персонально отфильтрованное.
- **Вывод:** ни у кого нет прямого аналога «устно поручили → тикет в Jira сам
  появился». Это и есть ниша MVP.

## Архитектурные решения

1. **Обработка — постфактум**, не в реальном времени. Задержка 1–3 минуты
   приемлема (у Otter — до 2 часов).
2. **Сопоставление имени с Jira-исполнителем — ручная таблица** имя→Jira
   username. Без календарной интеграции, без голосовой диаризации.
3. **Захват звука — переиспользуется код `~/Desktop/live_copilot_poc`
   без изменений**, не как библиотека, а как отдельный процесс: он уже пишет
   транскрипт в файл `transcripts/<timestamp>.txt`
   (`SystemAudioDump` + микрофон, два канала «Ты»/«Собеседник» через
   Speechmatics streaming). Формат строки:
   `[HH:MM:SS] <Ты|Собеседник>: текст`.
   - **Известное ограничение:** чистое разделение каналов работает только на
     встрече 1-на-1. На групповых созвонах (3+ участника) все голоса кроме
     своего смешиваются в канал «Собеседник» — модель на шаге детекта задач
     угадывает адресата по именам, названным вслух в самой речи, не по
     голосу/каналу.
4. **Jira** — используется существующий реальный аккаунт, заводится отдельный
   API-токен под этот проект.
5. **Обработка транскрипта — один проход LLM** по всему тексту сразу: найти
   задачу + определить исполнителя + сформулировать, всё одним вызовом. Без
   чанкинга. (Апгрейд на двухпроходную схему — только если на длинных звонках
   реально проявится пропуск задач из-за эффекта "lost in the middle".)
   **Конкретный провайдер/модель для этого вызова не зафиксирован в этом
   документе** — решается на этапе написания плана (writing-plans), не
   архитектурный вопрос сам по себе. Кандидат по умолчанию — тот же Groq
   (`openai/gpt-oss-120b`), что уже используется в `live_copilot_poc` (готовый
   ключ, проверенное качество), но альтернативы можно сравнить перед стартом
   реализации.
   **Защита от галлюцинации:** тот же класс LLM уже давал в `live_copilot_poc`
   выдуманные цитаты, поданные как реальный анализ (см. известный баг отчёта о
   сессии). Здесь это критичнее — ложное срабатывание создаёт настоящий тикет
   в Jira на несуществующую задачу. Двухслойная защита (см. Поток данных,
   шаг 6): (1) промпт явно требует, чтобы поле `цитата` было дословной
   выпиской из транскрипта, без перефразирования; (2) код после ответа LLM
   проверяет, что нормализованная цитата действительно встречается подстрокой
   в нормализованном тексте транскрипта — без сети, без второго вызова LLM.
6. **Несколько задач одному человеку за созвон — не отдельный случай.** LLM
   возвращает список задач; каждый элемент списка обрабатывается независимо
   (своё сопоставление имени, свой тикет), специальной логики агрегации по
   исполнителю не требуется (см. Поток данных).

## Компоненты и границы

Два независимых процесса, связанных только через файл — не общий код, не общий
процесс:

- **Захват** (`live_copilot_poc.py`, без изменений) — отвечает только за то,
  что во время звонка транскрипт пишется в
  `~/Desktop/live_copilot_poc/transcripts/*.txt`. Новый проект этот код не
  трогает и не импортирует.
- **Jira-пайплайн** (новый код, живёт в `~/Desktop/meeting_copilot/`) —
  отдельный CLI-скрипт, запускаемый вручную после звонка. Интерфейс между
  компонентами — сам файл транскрипта и его формат строки, задокументированный
  выше.

## Поток данных

1. Во время звонка — `live_copilot_poc.py` запускается как есть, пишет
   `transcripts/<timestamp>.txt`.
2. После звонка — Артём вручную запускает CLI-команду нового скрипта, без
   аргументов: скрипт сам берёт самый свежий файл в
   `live_copilot_poc/transcripts/`, которого ещё нет в
   `live_copilot_poc/transcripts/processed/`.
3. Скрипт загружает таблицу имя→Jira username (JSON/YAML-файл в
   `meeting_copilot/`, редактируется руками).
4. Если длина транскрипта ниже порога — обработка прекращается на этом шаге,
   без вызова LLM (см. Обработку ошибок).
5. Один вызов LLM: (полный текст транскрипта + таблица имён + инструкция) →
   структурированный JSON-список найденных задач вида
   `{кому: str, что: str, цитата: str}`.
6. **Проверка цитаты на галлюцинацию** — для каждой задачи из списка текст
   `цитата` и текст транскрипта нормализуются (нижний регистр, схлопнутые
   пробелы, без пунктуации) и проверяется вхождение подстрокой. Не найдена →
   задача помечается «требует проверки: цитата не найдена дословно в
   транскрипте», тикет не создаётся, обработка переходит к следующей задаче
   из списка (см. Архитектурные решения, п.5).
7. Для задач, прошедших проверку цитаты — сопоставление `кому` с
   Jira-логином по таблице (точное совпадение по имени). Не сопоставлено →
   задача помечается «пропущено: имя не найдено в таблице», тикет не
   создаётся.
8. Для каждой задачи, прошедшей оба фильтра — независимый вызов Jira REST API
   (create issue): исполнитель, текст задачи, цитата-источник в описании
   тикета. Ошибка на одном тикете не блокирует создание остальных.
9. Формируется единый текстовый отчёт: список созданных тикетов (со ссылками),
   список «требует проверки» (не прошли проверку цитаты), список «пропущено»
   (имя не сопоставлено), список ошибок Jira API.
10. Отчёт отправляется одним сообщением через прямой HTTP-вызов Telegram Bot
    API (`sendMessage`) — отдельный бот-токен, заведённый специально под этот
    проект через BotFather. Это не отдельный сервис — вызов происходит внутри
    того же CLI-скрипта.
11. Только если шаги 5–10 завершились без прерывания (см. Обработку ошибок) —
    обработанный файл переносится в
    `live_copilot_poc/transcripts/processed/`.

## Обработка ошибок

Принцип: явно сообщить и ничего не сделать лучше, чем тихо сделать неверно.
Файл транскрипта переезжает в `processed/` только по итогам полностью
успешного прогона.

| Ситуация | Поведение |
|---|---|
| Нет необработанного файла | Сообщение в терминал, выход без действий |
| Транскрипт короче порога | LLM не вызывается, отчёт «транскрипт слишком короткий, пропущен» |
| Таблица имён отсутствует/битая | Падение сразу с понятной ошибкой, дальше не идти |
| LLM-вызов упал (сеть/лимит/таймаут) | Прогон прерывается целиком, файл НЕ переезжает, в Telegram — «не удалось обработать, попробуй ещё раз» |
| LLM вернул невалидный JSON | Тот же путь, что при сбое вызова — файл не переезжает, сырой ответ логируется для дебага |
| Цитата задачи не найдена дословно в транскрипте (подозрение на галлюцинацию) | Тикет не создаётся, задача идёт в отчёт как «требует проверки», остальные задачи прогона не блокируются |
| Имя не сопоставлено с таблицей | Тикет не создаётся, попадает в отчёт как «пропущено» с цитатой |
| Jira API отклонил конкретный тикет | Не блокирует остальные тикеты этого прогона — ошибка идёт в отчёт, остальные создаются |

**Принятый риск, не решается в MVP:** если процесс упадёт уже ПОСЛЕ шага 5
(например, на середине создания тикетов), файл не переедет в `processed/`, и
повторный запуск может задвоить уже успешно созданные тикеты. Для маленькой
команды это редкий случай с дешёвой ручной починкой (удалить дубль в Jira) —
защита от него сейчас избыточна (YAGNI), возвращаемся к вопросу только если
реально столкнёмся на практике.

## Тестирование

Все внешние вызовы (LLM, Jira API, Telegram) по умолчанию мокаются в
автотестах; реальные обращения — только вручную, за явным флагом, не в
автопрогоне (по аналогии с `TWOGIS_API_KEY_REAL` в `idea_bot`).

1. **Модульные тесты чистой логики** (без сети):
   - выбор файла — из смеси файлов в `transcripts/` и `transcripts/processed/`
     берётся правильный самый свежий необработанный;
   - порог минимальной длины — короткий транскрипт пропускается, LLM не
     вызывается;
   - сопоставление имени с таблицей — совпадение находится, отсутствие
     помечается «не сопоставлено»;
   - проверка цитаты на подстроку — цитата дословно найдена в транскрипте
     (в т.ч. с разным регистром/пунктуацией/пробелами) → проходит; цитата
     перефразирована или отсутствует в тексте → помечается «требует
     проверки»;
   - сборка итогового текста отчёта из тестовых данных.
2. **Тесты с моками внешних вызовов**:
   - LLM вернул валидный JSON со списком задач, все цитаты дословные → пайплайн
     доходит до создания тикетов;
   - LLM вернул задачу с цитатой, которой нет в транскрипте (симуляция
     галлюцинации) → тикет не создаётся, задача в отчёте как «требует
     проверки», остальные задачи прогона обрабатываются как обычно;
   - LLM вернул невалидный JSON → путь ошибки (файл не переезжает, лог сырого
     ответа);
   - LLM упал по сети/лимиту → путь ошибки, файл не переезжает;
   - Jira создал один тикет успешно и один с ошибкой в одном прогоне →
     успешный не блокируется соседним, обе исход-записи в отчёте;
   - Telegram-отправка — мок, проверка правильного итогового текста.
3. **End-to-end тест на синтетическом fixture-транскрипте** — небольшой
   сочинённый файл в формате `[HH:MM:SS] Собеседник: ...` с одной чёткой
   задачей, полный прогон через все моки, проверка переноса файла в
   `processed/` только по итогам полного успеха.
   Дополнительный fixture-сценарий: та же схема, но LLM-мок возвращает задачу
   с сфабрикованной цитатой — проверка, что тикет не создаётся, а файл
   всё равно корректно переезжает в `processed/` (прогон завершился успешно,
   просто с задачей в категории «требует проверки», это не ошибка выполнения).
4. **Ручной прод-тест** (не в автопрогоне) — один реальный прогон на настоящий
   Jira-проект/токен + реальный LLM-вызов + реальное Telegram-сообщение,
   только руками, когда осознанно готов проверить живьём.

## Вне рамок этого MVP

- Вторая фича (подсказки из прошлых встреч для пропустивших созвон) — см.
  Контекст выше, отдельный раунд брейнсторминга.
- Календарная интеграция, голосовая диаризация, обработка групповых созвонов
  3+ (сверх известного ограничения по каналам).
- Автоматический (не ручной) триггер пайплайна после звонка.
- Защита от повторного запуска после падения процесса на середине (см.
  Обработку ошибок).
- **Окончательный выбор LLM-провайдера/модели** для детекта задач — не
  архитектурное решение, откладывается до writing-plans (см. Архитектурные
  решения, п.5); дефолтный кандидат по переиспользованию — Groq
  `openai/gpt-oss-120b`.
- Точное числовое значение порога «транскрипт слишком короткий» (символов) —
  параметр, фиксируется на этапе плана/реализации, не архитектурный вопрос.
