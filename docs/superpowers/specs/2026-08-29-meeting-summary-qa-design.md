# Meeting Copilot — саммари для саммари (Q&A по прошлым созвонам)

Дата: 2026-08-29
Статус: дизайн одобрен, spec написан, план реализации ещё не создан

## Контекст и гипотеза

Продолжение проекта после MVP по автопостановке задач в Jira (см.
`2026-08-27-jira-task-detection-mvp-design.md`). Это вторая из фич,
изначально описанных на уровне общего принципа при брейнсторминге
27 августа («если человек не был на созвоне, система подсвечивает именно
то, что касается лично его, а не отдаёт весь общий текст саммари на
прочтение») и детально не проработанных до этого документа.

**Идеальный сценарий целиком** (со слов Артёма, ориентир Fireflies.ai —
не строится сейчас целиком, только часть):
1. Отдельный bot-join агент подключается к звонку и слушает — вместо
   локального захвата.
2. После звонка — «саммари для саммари»: не общая краткая сноска, а
   конкретный список вопросов/тем, которые обсуждались, + краткие
   ответы/решения по каждому — чтобы пропустивший созвон человек мог
   полностью влиться в курс дела, а не просто «понять о чём был разговор».
3. Детект отсутствующих по календарю.
4. Автоматическое уведомление пропустившим.
5. Постановка задач в Jira (уже сделано, отдельный MVP).
6. Конечная точка — накопленная история прошлых обсуждений питает живые
   подсказки во время звонка (возрождение суфлёра из `live_copilot_poc`,
   но для рабочих созвонов, с памятью о прошлом).

**Этот документ строит только пункт 2** — генерацию и накопление
структурированного саммари. Пункты 1, 3, 4 явно отложены Артёмом (без
bot-join агента, без календаря — вместо детекта отсутствия и уведомления
выбрана pull-модель: человек сам спрашивает, когда ему нужно). Пункт 6 —
конечная цель, для которой этот документ закладывает сырьё (архив
саммари), но сам механизм живых подсказок не проектируется здесь.

## Архитектурные решения

1. **Без детекта отсутствия и без календаря.** Система не решает, кто
   пропустил созвон. Вместо этого человек сам, перед своим следующим
   созвоном, спрашивает «что я пропустил» — pull, не push.
2. **Канал запроса — уже существующий UI `live_copilot_poc`.** Там уже
   есть поле «Контекст» и векторный поиск «База знаний» — саммари
   подгружаются туда, и человек спрашивает текстом в том же окне, где
   работает живой суфлёр. Это прямой шаг к пункту 6 идеального сценария.
3. **Доставка в «Базу знаний» — вручную, через уже готовый UI
   `live_copilot_poc`, не автоматически.** `meeting_copilot` только
   сохраняет файл саммари на диск; загрузка в базу знаний — ручное действие
   человека. Сохраняет жёсткую границу, принятую ещё для Jira-MVP:
   `meeting_copilot` никогда не трогает код или внутренние файлы
   `live_copilot_poc`.
4. **Генерация — часть того же `run.py`, не отдельный скрипт.** Один
   прогон после звонка делает и детект задач, и саммари. Отдельный скрипт
   создал бы гонку: транскрипт может уже переехать в `processed/` после
   первого скрипта, и второй его не увидит.
5. **Формат файла — Markdown, читаемый текст**, список вопрос→ответ/решение,
   не JSON. `live_copilot_poc`'s «База знаний» эмбеддит обычные текстовые
   файлы (чанки по ~700 символов) — Markdown для этого естественный формат,
   и человек тоже может открыть и прочитать его сам глазами.
6. **Та же защита от галлюцинации, что и в Jira-детекте** —
   `quote_verification.verify_quote` переиспользуется без изменений. Каждая
   пара вопрос/ответ несёт дословную цитату-источник, непрошедшие проверку
   уходят в отдельную секцию «требует проверки», а не отбрасываются молча.
7. **Изоляция ошибок от уже существующего Jira-пайплайна.** Провал
   генерации саммари (второй, независимый LLM-вызов) никогда не блокирует
   уже успешно созданные тикеты и не мешает переносу транскрипта в
   `processed/` — иначе повторный запуск из-за несвязанного сбоя саммари
   рискует задвоить уже созданные тикеты (тот же класс риска, что уже
   принят и задокументирован в Jira-MVP).
8. **Переиспользование кода, не дублирование.** `LLMCallError` и
   `LLMResponseParseError` берутся из `task_extraction.py`, не
   переопределяются заново — это общий, не специфичный для задач тип
   ошибки одного Groq-вызова.

## Компоненты и границы

- **`summary_extraction.py`** (новый) — второй, независимый Groq-вызов:
  находит содержательные вопросы/темы и ответы/решения по ним в
  транскрипте. Не знает про Jira, про `task_extraction.py` не зависит,
  кроме двух переиспользуемых классов исключений.
- **`summary_markdown.py`** (новый) — чистая функция форматирования: список
  пар + список непрошедших проверку → готовый Markdown-текст. Аналог
  `report.py`, но для саммари, а не для Jira-отчёта.
- **`run.py`** (расширяется) — после успешного детекта задач (см. Поток
  данных) дополнительно вызывает эти два модуля, сохраняет файл, добавляет
  строку в Telegram-отчёт.
- **`report.py`** (расширяется) — новая необязательная строка в отчёте про
  исход генерации саммари.
- **`live_copilot_poc`** — не трогается кодом вообще. Единственная связь —
  человек сам открывает его UI и вручную добавляет файл в «Базу знаний»,
  когда ему это нужно.

## Поток данных

1. `run.py` уже прочитал транскрипт и успешно вызвал `task_extraction.extract_tasks`
   (детект задач для Jira, как в существующем MVP) — на этом этапе неважно,
   найдены ли задачи и есть ли рабочие Jira-креденшлы, важно только что сам
   транскрипт прошёл порог длины и первый Groq-вызов не упал с ошибкой.
2. Второй, независимый вызов: `summary_extraction.extract_qa_pairs(transcript, api_key)`
   → список `{question: str, answer: str, quote: str}`.
   - Системный промпт:
     ```
     Ты анализируешь транскрипт рабочего созвона между коллегами.
     Твоя задача — выделить содержательные вопросы или темы, которые
     реально обсуждались, и краткий ответ или принятое решение по каждому.

     Верни СТРОГО JSON-объект вида:
     {"items": [{"question": "о чём был вопрос/тема",
                  "answer": "какой ответ/решение",
                  "quote": "дословная цитата из транскрипта, подтверждающая это"}]}

     Правила:
     - Не пересказывай светскую беседу (приветствия, погода, личные темы) —
       только содержательные рабочие вопросы и решения.
     - Поле quote ОБЯЗАНО быть дословной выпиской из транскрипта,
       без перефразирования.
     - Если содержательного обсуждения не было — верни {"items": []}.
     - Не придумывай вопросы или решения, которых нет в тексте.
     ```
   - Та же валидация значений, что уже есть в `task_extraction.py` (ключи
     присутствуют, значения — непустые строки), та же пара исключений
     (`LLMCallError`, `LLMResponseParseError`), переиспользуемых из
     `task_extraction.py`.
3. Для каждой пары — `quote_verification.verify_quote(item["quote"], transcript)`.
   Не прошла — пара уходит в `needs_review`, не в основной список.
4. `summary_markdown.build_summary_markdown(meeting_label, qa_pairs, needs_review) -> str`
   собирает готовый текст:
   ```markdown
   # Саммари созвона — 2026-08-28 10:00

   ## Обсуждали

   ### Как обстоят дела с отчётом по продажам?
   Цифры так себе за прошлый квартал, нужно разобраться.

   ## Требует проверки (цитата не найдена дословно)

   - **Вопрос:** ...
     **Ответ (не подтверждён):** ...
   ```
   Если `qa_pairs` пуст и `needs_review` пуст — вместо секции «Обсуждали»
   пишется «Ничего существенного не обсуждалось.» (тот же принцип, что
   «Задач не найдено» в Jira-отчёте).
   `meeting_label` — читаемая дата/время, взятая из имени файла транскрипта
   (`2026-08-28_10-00-00.txt` → `2026-08-28 10:00`).
5. Файл сохраняется как `summaries/<то же имя, что у файла транскрипта>.md`
   (например, `summaries/2026-08-28_10-00-00.md`) — по имени сразу видно,
   какому звонку соответствует. Папка создаётся автоматически, если её ещё
   нет. **Папка `summaries/` не коммитится в git** — это личный рабочий
   контент, не пример для репозитория (добавляется в `.gitignore`).
6. В Telegram-отчёт (существующий `report.py`, расширяется) добавляется
   одна строка: путь к сохранённому файлу саммари, либо, если шаг 2 упал —
   отдельная пометка «не удалось сгенерировать саммари» без деталей ошибки
   LLM (полная ошибка — только в терминал, как и для остальных сбоев).
7. Дальше — ручной шаг человека, вне кода: перед следующим релевантным
   созвоном самому открыть `live_copilot_poc` и перетащить нужный файл
   саммари в поле «База знаний», после чего можно спросить текстом «что
   обсуждали по X в прошлый раз».

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Второй LLM-вызов упал (сеть/невалидный JSON) | Не блокирует уже созданные тикеты и перенос файла в `processed/`. В Telegram — «не удалось сгенерировать саммари» |
| Пустой список пар (созвон был чисто светской беседой) | Файл всё равно создаётся, с пометкой «Ничего существенного не обсуждалось» |
| Пара не прошла проверку цитаты | Не отбрасывается — уходит в секцию «Требует проверки» того же файла |
| Папки `summaries/` не существует | Создаётся автоматически при первом сохранении |

Явно **не** решается в этом раунде (сознательно, как и в Jira-MVP —
задокументированный остаточный риск, не забытый случай): если сам процесс
упадёт уже после успешного сохранения файла саммари, но до переноса
транскрипта в `processed/` — при повторном запуске саммари для этого звонка
будет сгенерировано заново и перезапишет предыдущий файл тем же именем.
Для одного человека это не создаёт задвоения (файл просто перезаписывается,
не размножается), в отличие от повторного создания тикета в Jira — поэтому
не требует отдельной защиты.

## Тестирование

Тот же принцип, что и в Jira-MVP: все внешние вызовы (второй Groq-вызов)
мокаются в автотестах.

1. **`summary_extraction.py`** — сокращённый набор моков относительно
   `task_extraction.py` (те же классы исключений уже покрыты тестами там,
   здесь — только специфика этого модуля):
   - валидный ответ с несколькими парами → корректный список;
   - пустой список `items` → пустой список на выходе;
   - сеть упала → `LLMCallError`;
   - невалидный JSON → `LLMResponseParseError`;
   - нестроковое/отсутствующее значение в паре → `LLMResponseParseError`.
2. **`summary_markdown.py`** — юнит-тесты на структуру:
   - обычные пары без проблем → корректный Markdown с датой и вопросами;
   - есть записи в `needs_review` → появляется секция «Требует проверки»;
   - оба списка пусты → «Ничего существенного не обсуждалось»;
   - `meeting_label` корректно подставляется в заголовок.
3. **`run.py` (end-to-end, с моками)**:
   - саммари генерируется и сохраняется по правильному пути одновременно с
     успешным созданием тикета в том же прогоне;
   - провал генерации саммари не блокирует уже созданные тикеты и перенос
     файла — прогон всё равно завершается успешно (файл в `processed/`);
   - пустой список пар всё равно создаёт файл с корректной пометкой.

## Вне рамок этого документа

- Bot-join агент вместо локального захвата.
- Календарная интеграция и детект отсутствующих.
- Автоматическое уведомление пропустивших созвон.
- Автоматическая загрузка саммари в «Базу знаний» `live_copilot_poc`
  (сейчас — ручной шаг человека).
- Живые подсказки во время звонка, питаемые накопленной историей —
  конечная цель всего направления, но отдельный, ещё не спроектированный
  этап.
