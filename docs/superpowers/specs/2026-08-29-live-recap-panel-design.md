# Meeting Copilot — авто-запуск обработки + панель «Прошлые созвоны» в суфлёре

Дата: 2026-08-29
Статус: дизайн одобрен, spec написан, план реализации ещё не создан

## Контекст и гипотеза

Третий кусок из идеального сценария (после MVP по Jira и Q&A-саммари) —
пункт 6 исходного брейнсторминга 27 августа: «живые подсказки во время
звонка, питаемые накопленной историей». В процессе уточнения выяснилось,
что то, что реально нужно Артёму — не поиск по базе знаний в реальном
времени (это уже работает в `live_copilot_poc` как есть, ничего чинить не
нужно), а **проактивный брифинг при следующем звонке**: «вот что обсуждали
в прошлый раз», без необходимости самому спрашивать.

Ключевой сдвиг в разговоре: Артём явно отверг усложнение через векторный
поиск/автозагрузку в «Базу знаний» («не думаю чтобы это было реализовано в
виде суфлёра... запись звука и транскрипт — не лучший вариант, чтобы он
мешался и показывался»). Вместо этого — простое чтение уже готового файла
с диска, без нового AI-решения в момент показа.

Второй сдвиг — обнаружился реальный разрыв в уже работающем пайплайне:
`meeting_copilot/run.py` запускается **вручную** после каждого звонка.
Артём прямо сформулировал желаемый идеал (дословно, по смыслу): «ты
запустил его (пока нет отдельного bot-join агента), закончил — прекратил
запись (пока нет агента, который поймёт что звонок закончился по
завершению конференции), и он автоматически делает саммари, а потом и то
что обсуждалось сразу в следующем звонке показывает, и делает задачи в
Jira». То есть детект «звонок закончился» = закрытие окна суфлёра (это
единственный доступный сигнал без bot-join агента, которого сознательно
нет в этом раунде — см. «Вне рамок»).

**Этот документ строит оба куска вместе**, потому что они образуют один
цикл: без авто-запуска `run.py` панель показывала бы только то, что
человек не забыл запустить руками, что подрывает саму идею «не думать об
этом».

## Архитектурные решения

1. **Триггер авто-запуска — уже существующий хук `on_closed()`** в
   `live_copilot_poc.py:1357`. Ничего нового не детектится: закрытие окна
   суфлёра уже останавливает аудио-потоки и закрывает файл транскрипта —
   это и есть естественная граница «звонок закончился» для этого раунда.
2. **Запуск — неблокирующий фоновый subprocess**, не импорт кода
   `meeting_copilot` в процесс `live_copilot_poc`. У проектов разные venv
   с разными зависимостями (Groq/Jira-клиент против Speechmatics/pywebview)
   — общий процесс технически не соберётся. Сохраняет и уже принятую
   границу «`meeting_copilot` не трогает код `live_copilot_poc`»
   (направление здесь обратное — `live_copilot_poc` **запускает**
   `meeting_copilot` как внешнюю программу, не переиспользует код —
   граница не нарушена).
3. **Панель «Прошлые созвоны» — чистое чтение файла с диска**, без
   эмбеддингов, без вызова LLM в момент показа. Файлы в `summaries/` уже
   прошли проверку цитатами при генерации (Q&A-саммари, живьём
   протестировано 29 авг) — повторного AI-решения при показе не требуется,
   и в этом весь смысл: пользователь читает уже проверенные данные, не
   ждёт новый ответ модели.
4. **Панель разворачивается сама при старте окна**, не по кнопке — это и
   есть «сноска сразу тут же» из исходного описания. Показывает файл с
   самой свежей датой; остальные доступны в том же списке.
5. **Свежесть данных не гарантирована в момент показа.** Между закрытием
   предыдущего звонка и открытием следующего фоновый `run.py` уже успеет
   отработать (обычно секунды-минуты, LLM-вызовы быстрые) — но это не
   железная гарантия, гонка теоретически возможна. Не решается отдельным
   механизмом ожидания в этом раунде (см. «Обработка ошибок») — цена
   ошибки низкая (показывается чуть более старый файл, не ничего).

## Компоненты и границы

- **`live_copilot_poc.py`, функция `on_closed()`** (расширяется) — в конце
  существующей функции, после уже происходящей остановки аудио и закрытия
  файла транскрипта, добавляется вызов нового вспомогательного
  `_trigger_meeting_copilot_run()`.
- **`live_copilot_poc.py`, новая функция `_trigger_meeting_copilot_run()`**
  — `subprocess.Popen` с venv-python `meeting_copilot`, `cwd` = директория
  `meeting_copilot`, `start_new_session=True` (не убивается при выходе
  родительского процесса), stdout/stderr перенаправлены в лог-файл (не в
  Jira/Telegram — это уже делает сам `run.py` при успехе). Обёрнуто в
  `try/except Exception`, ошибка запуска (например, venv не найден) не
  должна ломать уже существующую логику закрытия окна.
- **`live_copilot_poc.py`, новые константы** — `MEETING_COPILOT_DIR`
  (`~/Desktop/meeting_copilot`), `MEETING_COPILOT_SUMMARIES_DIR`
  (`<MEETING_COPILOT_DIR>/summaries`), `MEETING_COPILOT_AUTO_RUN_LOG`
  (`<MEETING_COPILOT_DIR>/auto_run.log` — не в git, личный рабочий лог,
  как и `summaries/`).
- **`live_copilot_poc.py`, новые методы `Api`** —
  `list_past_summaries()` (список файлов из `MEETING_COPILOT_SUMMARIES_DIR`,
  отсортированных по дате из имени файла, новые сверху) и
  `read_summary(filename)` (текст одного файла). Оба — чтение с диска,
  без сети.
- **`live_copilot_poc.py`, новая секция в HTML/JS** — «Прошлые созвоны»,
  тот же паттерн сворачиваемой секции, что уже есть у «Транскрипт»/
  «Карточки», но развёрнута по умолчанию при загрузке окна (вызывает
  `list_past_summaries()` сразу в `after_start`/при инициализации JS, не
  по клику кнопки). Список кликабельных файлов, клик подгружает текст
  через `read_summary(filename)` и рендерит его в тот же блок.
  Оформление — по принципам скилла `apple-design` (плавное появление
  списка/текста, типографика, соответствие уже существующей эстетике
  окна).
- **`meeting_copilot`** — не меняется вообще. `run.py` уже делает всё
  нужное (саммари + Jira), просто теперь вызывается автоматически, а не
  руками.

## Поток данных

1. Пользователь открывает `live_copilot_poc` — `after_start()` (без
   изменений) начинает запись, JS сразу вызывает
   `list_past_summaries()` и разворачивает панель с самым свежим файлом.
2. Звонок идёт, всё как раньше — захват звука, живые подсказки, если
   нужны, без изменений.
3. Пользователь закрывает окно → `on_closed()` (расширена): существующая
   остановка аудио/закрытие файла транскрипта — без изменений, **плюс**
   в конце вызывается `_trigger_meeting_copilot_run()`.
4. `_trigger_meeting_copilot_run()` запускает `meeting_copilot/run.py`
   как отдельный процесс, не дожидаясь его завершения — окно суфлёра
   закрывается сразу, не блокируется на время LLM-вызовов.
5. `run.py` (без изменений) сам находит только что закрытый транскрипт,
   генерирует саммари в `summaries/` и тикеты в Jira, шлёт отчёт в
   Telegram — весь этот путь уже реализован и живьём протестирован.
6. Следующий раз пользователь открывает `live_copilot_poc` → шаг 1
   повторяется, новый файл уже виден в панели.

## Обработка ошибок

| Ситуация | Поведение |
|---|---|
| `venv` `meeting_copilot` не найден / `subprocess.Popen` не смог стартовать | Ошибка ловится в `try/except`, пишется в лог-файл, `on_closed()` продолжает и завершается штатно — закрытие окна суфлёра никогда не блокируется и не падает из-за этой фичи |
| `run.py` упал уже после старта (сеть, невалидные credentials) | Не видно в реальном времени (нет открытого терминала) — stdout/stderr `run.py` перенаправлены в лог-файл на диске, чтобы не потерять причину молча. Успешные прогоны и так шлют отчёт в Telegram (уже существующее поведение) |
| Гонка: панель открылась раньше, чем фоновый `run.py` успел отработать | Показывается файл с прошлого раза (не ничего) — не отдельный механизм, цена ошибки низкая |
| `read_summary(filename)` получает имя файла из JS (со стороны клиента в webview) | Путь строится и проверяется на принадлежность `MEETING_COPILOT_SUMMARIES_DIR` (без выхода наружу через `..` или абсолютный путь) — простая защита от обращения к произвольному файлу на диске через этот канал |
| Папки `summaries/` не существует (ни разу не запускался `run.py`) | `list_past_summaries()` возвращает пустой список, панель показывает нейтральное «пока нет прошлых созвонов» вместо ошибки |

## Тестирование

`test_poc.py` уже устроен в двух частях: бэкенд-юниты без API и
Playwright-тесты живого Chromium против HTML, извлечённого из модуля, с
`pywebview.api`, подменённым заглушкой-логгером (уже так проверяются
кнопки/чипы/пузыри подсказок) — это и есть готовый паттерн для новой
JS-части панели, не что-то новое.

- **Бэкенд-юниты** (часть 1, без API): `list_past_summaries()` —
  сортировка по дате из имени файла, пустой список при отсутствующей
  папке; `read_summary(filename)` — корректное чтение и защита от path
  traversal (`../`, абсолютный путь); сборка команды `subprocess.Popen` в
  `_trigger_meeting_copilot_run()` — без реального запуска `run.py`.
- **Playwright-часть (часть 2)**: рендер списка файлов в панели,
  разворачивание секции при загрузке (без клика), клик по файлу
  подставляет текст саммари в блок — тем же способом, что уже проверяет
  чипы/пузыри в существующих тестах.
- **Не покрывается автотестами** (как и остальной lifecycle в этом
  файле) — сам факт вызова `_trigger_meeting_copilot_run()` из реального
  `on_closed()` при закрытии настоящего окна, и то, что фоновый процесс
  действительно переживает выход родителя. Это и раньше было вне
  автотестов (`test_poc.py` прямо документирует: «не проверяет... живой
  тест человеком») — здесь тот же принцип: ручная живая проверка —
  открыть суфлёр, короткий тестовый звонок, закрыть окно, подождать,
  открыть снова и убедиться что панель показывает свежий файл (аналогично
  уже пройденной живой проверке `run.py` и Q&A-саммари).

## Вне рамок этого документа

- Bot-join агент и настоящий детект «конференция завершилась» —
  сознательно не строится, закрытие окна суфлёра остаётся единственным
  сигналом в этом раунде.
- Календарная интеграция, привязка звонка к конкретным участникам/теме —
  панель показывает просто самый свежий файл, не «релевантный именно
  этому звонку» (это пункт 3 исходного идеального сценария — детект
  отсутствующих по календарю, — ещё не спроектирован отдельно).
- Ожидание/синхронизация, чтобы гарантированно не открыть панель раньше,
  чем фоновый `run.py` успеет отработать — принят как низкий,
  недорогой остаточный риск.
- Автоматическая загрузка файлов саммари в «Базу знаний» для векторного
  поиска во время звонка — осталось решение из прошлого раунда: ручной
  шаг, отдельный от этой панели.
